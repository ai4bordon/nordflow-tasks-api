# NordFlow Tasks — бэкенд трекера проектов и задач

MVP внутреннего трекера для компании NordFlow: проекты, задачи с Kanban-доской,
роли, комментарии, история изменений, уведомления и поиск.

**Источник:** ТЗ клиента NordFlow из урока FGIp07 (файл `tz.txt` — документ курса, в репозиторий не выкладывается). Рыночный аналог похожего заказа:
[Weblancer #1253818, разработка сервиса планирования задач](https://www.weblancer.net/freelance/veb-programmirovanie-31/razrabotka-veb-prilozheniya-servisa-planirovaniya-zadach-1253818/).

## Что сделано в этом кейсе

Только **бэкенд**: домен, права доступа и HTTP API. Интерфейса здесь нет —
для него отдельно написан [ТЗ для дизайнера](ТЗ_для_дизайнера.md) с функциональными
требованиями и пользовательскими сценариями.

## Запуск

Нужен Node.js 20+ и ничего больше: зависимостей нет, сборки нет.

```bash
cd case1-nordflow-tasks
node server.js
```

Сервис поднимется на `http://localhost:3000`. При первом запуске в `data/store.json`
запишутся демонстрационные данные из ТЗ (8 сотрудников, 3 проекта, 25 задач).

Демо-учётки (пароль у всех — `nordflow`):

| Почта | Роль | Что видит |
| --- | --- | --- |
| `anna@nordflow.io` | администратор | всё, включая управление пользователями |
| `maxim@nordflow.io` | руководитель проектов | свои проекты, сводку по команде |
| `ilya@nordflow.io` | сотрудник | только свои задачи и проекты участия |

Проверка тестами:

```bash
node --test test/app.test.mjs
```

## Архитектура

```text
src/app.js     ядро: домен, права доступа, таблица маршрутов. Про HTTP не знает.
server.js      тонкий адаптер: node:http, разбор JSON, передача запроса в ядро
test/app.test.mjs  тесты бьют прямо в ядро — порт и файлы не нужны
data/store.json    состояние (создаётся при первом запуске, в git не попадает)
```

Ядро отделено от HTTP намеренно: тесты вызывают `app.dispatch(method, path, { body, token })`
и проверяют бизнес-логику без сети и без записи на диск. Один и тот же код можно
потом завернуть в любой фреймворк или вынести в serverless без переписывания домена.

Роли и права проверяются в каждом обработчике: сотрудник не видит чужие проекты,
руководитель правит задачи своих проектов, администратор управляет людьми и архивами.

## API

Авторизации нет только у входа. Токен передаётся заголовком `X-Token`.

| Метод | Адрес | Кто может | Назначение |
| --- | --- | --- | --- |
| POST | `/api/login` | все | вход по почте и паролю, выдаёт токен |
| POST | `/api/logout` | вход | выход, токен перестаёт работать |
| GET | `/api/me` | вход | текущий пользователь |
| GET | `/api/dashboard` | вход | счётчики, ближайшие сроки, свежие изменения, мои проекты, сводка по команде |
| GET | `/api/users` | вход | команда с загрузкой и просрочками |
| POST | `/api/users` | админ | создать сотрудника |
| PATCH | `/api/users/:id` | админ — любого, сотрудник — себя | имя, должность, тема, пароль; почту и роль меняет только админ |
| DELETE | `/api/users/:id` | админ | удалить сотрудника |
| GET | `/api/projects` | вход | доступные проекты с количеством задач и участников |
| POST | `/api/projects` | админ | создать проект |
| GET | `/api/projects/:id` | участник, админ | карточка проекта с участниками |
| PATCH | `/api/projects/:id` | админ, руководитель проекта | поля, статус, участники |
| POST | `/api/projects/:id/archive` | админ | в архив |
| POST | `/api/projects/:id/members` | админ, руководитель | добавить участника |
| DELETE | `/api/projects/:id/members/:userId` | админ, руководитель | убрать участника |
| GET | `/api/projects/:id/board` | участник, админ | Kanban-доска: 5 колонок с карточками |
| GET | `/api/tasks` | вход | задачи с фильтрами и поиском |
| POST | `/api/tasks` | админ, руководитель, сотрудник если разрешено проектом | создать задачу |
| GET | `/api/tasks/:id` | участник проекта | задача, комментарии, история изменений |
| PATCH | `/api/tasks/:id` | автор, руководитель, админ; исполнитель — статус | правка полей и статуса |
| POST | `/api/tasks/:id/status` | исполнитель, руководитель, админ | перемещение карточки между колонками |
| POST | `/api/tasks/:id/comments` | участник проекта | комментарий |
| PATCH | `/api/comments/:id` | автор комментария | правка своего комментария |
| DELETE | `/api/comments/:id` | автор, админ | удалить комментарий |
| GET | `/api/notifications` | вход | уведомления: назначение, срок, статус, комментарий, приближение и просрочка |
| POST | `/api/notifications/:id/read` | вход | отметить прочитанным |
| POST | `/api/notifications/read-all` | вход | отметить всё |
| GET | `/api/search?q=` | вход | поиск по проектам, задачам и сотрудникам |

Фильтры `/api/tasks`: `scope=my`, `projectId`, `status`, `priority`, `assigneeId`,
`overdue=1`, `due=week`, `q`. Статусы: `backlog`, `planned`, `in_progress`, `review`, `done`.
Приоритеты: `low`, `medium`, `high`, `critical`.

## Тесты

`node --test test/app.test.mjs` — 13 тестов, каждый соответствует пункту критериев
приёмки ТЗ (раздел 26): вход и выход, создание проектов и пользователей, задача
с исполнителем, Kanban и смена статуса, комментарии и права, фильтры и поиск,
просрочки, уведомления, сводка для роли, изоляция проектов, объём демо-данных.

Первый прогон показал три падения, все три оказались настоящими проблемами:
сотрудник не мог двигать свою задачу (права на поля и на статус были склеены в одну
проверку), поиск не находил «Вёрстка» по запросу «верстк» (буква «ё»), в демо-данных
не хватало просроченных задач для руководителя. Исправлено в логике, а не подгонкой тестов.

## Что осознанно не вошло (по ТЗ, раздел 25)

Видеозвонки, чат между сотрудниками, диаграмма Ганта, учёт часов, интеграции
с Telegram и почтой, импорт из Jira, кастомные типы задач, несколько рабочих
пространств, платная подписка. Уведомления — только внутри приложения,
как и требует ТЗ.
